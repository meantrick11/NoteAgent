# 编码架构与 Git 交付

本 skill 规定**做决定和验证的顺序**。当前仓库的实例见 [NoteAgent 目录约定](references/noteagent-layout.md)。用户要求和仓库现有明确约定优先；目录示例不能替代对实际代码的检查。

## 1. 先确定变更边界

1. 读取任务涉及的入口、调用链、测试、配置和现有目录；检查 `git status`、当前分支及仓库约定。记录已有未提交改动，保持原样。
2. 写明本次改变的业务能力、对外接口、数据格式和不变量。无法确定模块归属时，依据“谁拥有业务规则和数据”判断；仍有多个合理归属时说明取舍。
3. 修改范围只覆盖目标能力及其必要的导入、测试、配置和文档。以现有行为作为重构基线；目录迁移本身不改变 HTTP 路径、数据库结构、持久化格式或错误语义。

完成标准：能指出每个拟修改文件的模块归属，以及迁移前后需要保持的行为。

## 2. 按业务能力组织代码

- 顶层保留应用装配、业务模块、跨模块基础能力和前端托管等清晰职责。具体 HTTP 端点进入所属业务模块的 `Router/`；顶层装配文件只注册路由和连接依赖。
- 一个业务能力在一个模块内闭合：`Router/` 处理协议，`Domain/Dto/` 放请求响应，`Domain/Vo/` 放业务值，`Domain/Po/` 放持久化模型，`Service/` 编排用例，`Mapper/` 处理数据库读写。只有确有职责时才建目录。
- 非数据库适配按真实职责命名，例如 `Storage/`、`Parser/`、`Provider/`、`Engine/`、`Agent/`。复杂子系统可在模块内继续按职责分层，避免同一目录堆放所有实现。
- `Common/` 只收纳已被多个模块复用、且没有单一业务所有者的能力。跨模块流程由明确的用例或装配点协调，优先通过稳定接口调用；保持现有事务边界，不能为追求目录纯度破坏原子性。
- 选择模块时优先使业务规则、修改原因和测试集中；避免只转发调用的浅层类、循环依赖和为了未来需求预设的空目录。

完成标准：从一个功能入口能沿本模块的 Router → Service → Domain/适配实现找到行为；例外的跨模块调用有明确原因。

## 3. 安排仓库外围文件

- 应用源码、前端工程、测试、数据库迁移、一次性脚本、可复用工具、评测数据与报告、当前文档、容器配置分别放在对应顶层目录。
- 测试按层级和业务模块归类；全应用共用的数据库迁移链放在应用级目录。生成产物、运行数据、密钥和本地缓存按仓库忽略规则处理。
- 源码路径变化时同步维护导入、构建输出、打包声明、容器复制路径、脚本、测试和当前文档。历史记录保留原貌，除非任务明确要求修订。

完成标准：运行入口、构建和文档都指向新路径，旧路径无活跃引用。

## 4. 按可回退的 Git 流程交付

1. 修改前检查状态；较大变更从正确基线创建独立工作分支，按仓库分支规范命名。保护 `main`/`master`，不在其上直接开发。
2. 对迁移优先使用 `git mv`，核对大小写敏感性、未跟踪文件与忽略文件。已有用户改动不擅自覆盖、暂存或提交。
3. 多步骤任务在开始前划分可独立验证的提交点；每完成一个业务模块、接口链路或迁移阶段，就验证该阶段并提交一次。目录迁移应将同一模块的文件移动、导入修正和对应测试放在同一提交，使该提交可运行、可回退。不要把整个任务积压到最后一次提交，也不要按文件数机械拆分。
4. 每次只暂存该阶段的目标文件，检查 `git diff --cached --check`、暂存清单和必要测试。不得混入用户已有改动、密钥或生成文件；验证失败的阶段先修复再提交。
5. 所有提交遵循 Conventional Commits：`<type>(<scope>): <中文祈使描述>`，按变更性质选用 `feat`、`fix`、`refactor`、`test`、`docs`、`chore`、`build`、`ci`、`perf`。例如 `refactor(notes): 调整笔记模块目录`、`test(notes): 补充目录迁移回归测试`。破坏性变更在类型或 scope 后标注 `!`，并在提交正文用 `BREAKING CHANGE:` 说明迁移影响；一个提交只表达一个明确目的。
6. 合并、推送、删除分支和发布遵循用户授权及仓库规则；推送前确认远端分支状态，防止覆盖他人提交。

完成标准：提交历史能按阶段还原实施过程；每个提交范围明确、已验证且可独立回退，分支来源和远端去向可追溯。

## 5. 验证与交付说明

先运行覆盖变更的单元测试，再运行相关集成测试、构建与必要的启动检查；目录重构还要检查旧导入和资源路径。失败时定位原因并修复，不能用测试数量代替关键链路验证。外部服务不可用时记录未完成的验证范围。

交付时说明模块职责变化、迁移范围、验证结果、剩余风险和用户原有改动的状态。若现有结构已经满足目标，说明核对证据，只处理实际残留。
