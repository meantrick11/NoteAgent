## 3. 检索层基线（dev 24 条）

配置：`all-MiniLM-L6-v2`（revision 见 `config.json`）、字符切块 500/50、Chroma 默认 L2、top_k=5、probe_k=20。

| 指标 | 结果 |
|---|---|
| full Evidence Recall@5 | 5/18 = 27.8% |
| mean Evidence Recall@5 | 0.278 |
| Evidence Hit@3 | 3/18 = 16.7% |
| MRR@5 | 0.164 |
| mean Evidence Recall@20（诊断） | 0.694 |
| mapping_error 片段数 | 0 |

按类别：

| 类别 | full Recall@5 | mean Recall@20 | MRR@5 |
|---|---|---|---|
| fact | 3/7 | 0.714 | 0.321 |
| mixed_language | 2/3 | 1.000 | 0.233 |
| multi_evidence | 0/4 | 0.875 | 0.000 |
| paraphrase | 0/4 | 0.250 | 0.000 |

失败分类（13 条未完全覆盖）：

| 分类 | 条数 | 含义 |
|---|---|---|
| `ranked_below_top_k` | 8 | 放到前 20 名就能覆盖，纯粹是排序问题 |
| `evidence_not_in_returned_fragments` | 5 | 返回的片段里没有能完整覆盖的证据 |

**解读。** 中英术语混合类在深候选里 100% 可覆盖，说明内容都在索引里，只是 MiniLM 的排序把正确片段压到后面。`paraphrase` 与 `multi_evidence` 两类 mean Recall@20 也只有 0.25 / 0.875，说明同义改写和多证据问题更依赖语义表示质量——这两类是任务 7（换向量模型）的主要受益面。

**性能（本机，CPU）**：索引 10 篇约 2.6–3.1 s；热查询 min 7.0 ms、p50 9.2 ms、p95 11.1 ms。同一 run 在不同时段测得 p95 从 11 ms 到 235 ms，说明本机其他进程会显著干扰延迟；跨 run 比较以 `min_ms` 为准，报告中同时保留 p50/p95。

## 4. Agent 层基线（dev 12 场景 × 3 次 = 36 轮）

配置：真实 `ChatAgent` + 真实四工具 + 真实 `RetrievalService`（工具内 `top_k=3`，与生产一致）+ 生产 `system.txt`（v9）。每个 case 独立沙箱：自己的 `notes/` 副本、自己的 Chroma、自己的 sqlite 会话库。**0 次运行异常，0 次 harness 不一致。**

| 指标 | 结果 | 门槛 | 判定 |
|---|---|---|---|
| Agent 任务成功率（历史场景） | **25/30 = 83.3%** | >= 85% | 未达 |
| Agent 任务成功率（严格引用口径） | 22/30 = 73.3% | — | 诊断 |
| 历史任务检索调用率 | **26/30 = 86.7%** | >= 90% | 未达 |
| 无需检索误调用率 | **0/6 = 0%** | <= 10% | 达标 |
| 普通对话不写盘 | **6/6 = 100%** | 确定用例全过 | 达标 |
| 历史无答案正确处理率 | **3/6 = 50%** | >= 90% | 未达 |
| 检索片段覆盖必需证据 | 15/24 = 62.5% | — | 诊断 |
| 靠 `read_file` 兜回正确笔记 | 7/30 = 23.3% | — | 诊断 |
| 引用可定位到文件 | **32/32 = 100%** | 100% | 达标（文件级） |
| 引用带回引文（可到章节/原文） | 18/32 = 56.3% | 100% | 未达 |

按场景：

| scenario | task success | strict | search called |
|---|---|---|---|
| history_answer | 12/12 | 9/12 | 12/12 |
| history_append | 10/12 | 10/12 | 8/12 |
| history_unanswerable | 3/6 | 3/6 | 6/6 |
| plain_chat | 6/6 | 6/6 | 0/6 |

逐 case（3 次里的成功次数）：

| case | success | strict | 说明 |
|---|---|---|---|
| a01 | 3 | 0 | 检索返回的是别的篇，靠 `read_file` 读对 Backtracking 后作答 |
| a02 | 3 | 3 | 省略主题的多轮提问，检索与引用都正确 |
| a03 / a04 | 3 / 3 | 3 / 3 | 中英术语查询，引用可到原文 |
| a05 | 3 | 3 | 识别出内容已存在，说明后不重复写入 |
| **a06** | **1** | 1 | **2 次直接 `replace` 掉原结论、未指出冲突** |
| a07 | 3 | 3 | 指出冲突后按冲突处理，未破坏原有内容 |
| a08 | 3 | 3 | 正确追加、保留原有事实（全程未检索，走 `list_files` + `read_file`） |
| a09 | 1 | 1 | 2 次未说明"笔记里没有" |
| a10 | 2 | 2 | 1 次未说明"笔记里没有" |
| a11 / a12 | 3 / 3 | 3 / 3 | 普通对话不检索、不写盘 |

**四条可行动结论：**

1. **检索工具是当前最弱的一环，Agent 在替它兜底。** `history_answer` 宽松口径 12/12，但严格口径只有 9/12，且 7 次运行是靠 `read_file` 读到正确笔记才答对的——检索片段本身只有 62.5% 覆盖必需证据。这与检索层"排序问题"完全一致。
2. **历史无答案场景有编造依据的风险。** 6 次里有 3 次没有明确说明"未找到"，而是直接作答。这是 50% 对 90% 门槛的主要缺口，也是任务 8 的第 3、5 项。
3. **冲突处理存在写入安全缺口。** a06 有 2 次把用户说错的结论直接 `replace` 写进笔记，丢掉了原有正确事实且没有指出冲突（`must_preserve=false`）。虽然写盘仍走人审，但这属于"草稿本身不安全"。
4. **追加场景 4/12 次没有检索。** 其中 a08 全程用 `list_files` + `read_file` 找到目标——按计划口径这是合法路径（"允许中间出现 `list_files`"），所以不计任务失败，但调用率因此只有 86.7%。

## 5. 失败归因汇总（批次 1）

批次 1 的失败**不用于评价系统好坏**，而用于决定批次 2 先改什么：

| 观察 | 证据 | 指向 |
|---|---|---|
| 主要内容都在索引里，但排序差 | probe@20 = 12/18 vs recall@5 = 5/18 | 任务 7（换向量模型）优先级最高 |
| 同义改写与多证据问题最差 | paraphrase / multi_evidence 的 mean Recall@20 仅 0.25 / 0.875 | 任务 7，其次任务 6（章节切块让证据更集中） |

| 语料本身有真实缺陷 | 见 §6：`Backtracking` 两节重复、6 处标题前缺空行 | 任务 5（先修笔记再归因于 embedding） |
| 无答案时直接作答 | 3/6 次未说明"未找到" | 任务 8 的第 3、5 项（证据不足要先说不足） |
| 冲突时 replace 掉原结论 | a06 2/3 次 `must_preserve=false` | 任务 8 的第 3 项（冲突要澄清，不得静默覆盖） |

## 8. 已知限制

1. **语料只有 10 篇、dev 24 / holdout 16**，门槛附近一条查询约等于 4–6 个百分点；报告一律同时给成功数/总数。
2. **自动审查不是独立验收**：关键词判定（未找到/重复/冲突）只是确定性代理，完整回答与草稿在 `var/` 的完整报告里，需人工确认。
3. **本机延迟噪声大**，只在同一时段的相对比较中有效。
4. **holdout 未使用**：本批只跑 dev。选定候选项后再跑 holdout；一旦据其失败改方案，该集合即视为已见，须追加新样本。
5. 语料中 9 篇 `source_status=missing`，因此**只判可读性与内部一致性**；只有 `Python_Tutorial_Intro` 有同章原文可比对，且不能证明该笔记正由该文本生成。
