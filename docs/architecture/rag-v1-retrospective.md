# RAG v1 复盘：问题、做法与结果

本文记录 2026-09-25 这一轮「检索质量」工作**遇到什么问题、用什么方式解决、效果如何、还剩什么**。它是复盘，不是规格：
现行实现看 [architecture.md](./architecture.md) 与 [retrieval.md](./retrieval.md)，度量契约看
[rag-quality.md](../evaluations/rag-quality.md)，逐次实验与失败样例看 [rag-v1-report.md](../evaluations/rag-v1-report.md)，执行计划看 [2026-09-25-rag-quality-improvement.md](../plans/2026-09-25-rag-quality-improvement.md)。

## 0. 主干

| 阶段 | 当时的问题 | 手段 | dev 效果（Evidence Recall@5） |
|---|---|---|---|
| 基线 | 说不清检索到底行不行 | 冻结 10 篇语料 + 40 条证据标注查询 + 真检索评测 | 5/18 = 27.8% |
| 切块 | 块跨章节、标题与正文分离；47% 的块超模型输入上限 | 章节感知切块 + 章节路径进嵌入文本 | 9/18 = 50% |
| 模型 | 中文与中英混排语义表示弱 | 候选对照选型（BGE-zh / 多语言 e5） | **17/18 = 94.4%** |
| 工具与 Agent | 片段不可定位；无答案时把背景当答案；冲突时静默覆盖原结论 | 片段带定位 + 判定口径修正 + 提示词 v10 | holdout 任务成功率 18/18 |

holdout（此前从未运行过）：检索 **6/12 → 11/12**，Agent 任务成功率 **17/18 → 18/18**。

## 1. 问题与解决

### 产品侧

| # | 现象 | 怎么定位 | 做法 | 效果 | 代价 / 残留 |
|---|---|---|---|---|---|
| P1 | 正确片段在候选里但排不进前 5 | 直接检索评测加 `--probe-k 20`，把"排 5 名之后"与"根本没召回"分开 | 章节感知切块（`heading`）：短章节整块保留，块不再跨节；标题解析做成**围栏感知**，代码注释里的 `#` 不再被当标题 | dev 5/18 → 9/18（hit@3 3→8） | 块数 107 → 176，索引耗时上升约 20% |
| P2 | 近一半的块被模型**静默截断** | 用模型自己的 tokenizer 实测每块 token 数并写进报告 | 把 `max_seq_length` 作为选型第一条判据；报告新增 `token_budget` | 截断 50/107 → 0/176 | 换模型带来体积与内存代价（见 P4） |
| P3 | 同一块内容在不同小节里语义不同，但向量一样 | 分类别看指标：`mixed_language` 反而变差 | 把 `heading_path` 拼进**被嵌入的文本**；引用原文仍存正文切片 | dev 9/18，混排类恢复 | 多一份"嵌入文本 ≠ 引用文本"的复杂度，代码里显式分开 |
| P4 | 中文 + 英文术语混排下语义表示弱 | 固定切块/距离/top-k，只换模型做对照 | 候选：BGE-small-zh（中文轻量）与 multilingual-e5-small（多语言）。**排除** paraphrase-multilingual-MiniLM（上限仅 128 token，比基线还低）与 BGE-M3（2.27GB、CPU 上算力约 25 倍，撞性能门槛） | dev 17/18 = 94.4%，holdout 11/12；截断归零 | 权重 91MB→471MB、参数 22.7M→117.7M、内存约 +350MB、查询延迟约 1.6 倍（仍在 2 倍门槛内） |
| P5 | 片段只给 `content` 和 `source_id`，模型要猜是哪个文件、哪一节 | 读 Agent 轨迹：模型为确认位置额外 `read_file` 整篇 | 片段**始终**带 `file_name` / `heading_path` / `start_char` / `end_char`，与是否有引用 registry 无关 | 靠 `read_file` 兜回 7/30 → 4/30 → **0/18（holdout）** | 工具返回体变大，token 成本略升（未单独测） |
| P6 | 用户说法与笔记冲突时，模型直接 `replace` 掉原有正确结论 | 把冲突场景做成固定 case（a06），跑 3 次看分布 | 提示词 **v10**：冲突时先指出冲突与原文依据、问清按哪个，不直接 replace | a06 0/3 → 3/3（holdout 同类场景 3/3） | 提示词改动必须重跑笔记质量回归（已做，见 §3） |
| P7 | 换了模型或切块，旧向量还在，检索**静默用错** | 设计时就把"配置 → 索引"绑定成指纹 | collection metadata 存指纹 `切块策略\|模型\|嵌入文本\|编码指令`；不符时构造服务即抛 `IndexConfigMismatch` 要求重建；加指纹前的旧索引按 legacy 默认处理，配置没变仍可用 | 换配置无法"忘记重建" | 代价是换配置必须先重建；生产切换由用户执行（报告 §6.4） |

### 评测侧（这一组和产品缺陷一样会误导决策）

评测本身出过 6 个问题，其中 4 个是"让指标失真"而不是"让功能坏掉"。**如果只看分数不看测量怎么来的，会把正确的行为判成失败、或把失败当通过。**

| # | 问题 | 后果 | 做法 |
|---|---|---|---|
| M1 | 应用读文本时会 CRLF→LF 规范化，而证据偏移按原始字节算 | 3 条查询出现假"映射错误" | 偏移基准改为**应用实际读到的文本**；写入前用切片校验 `text[start:end] == content` |
| M2 | 流式 `tool` 事件携带的参数不完整（常常是 `{}`） | "提案前是否读过目标文件"被误判 | 轨迹改用**落库的 tool stub**（执行后写入，含完整参数与状态） |
| M3 | 重复内容检查查的是目标文件 | 原文本来就有那段 → 判定永远为假 | 改查**草稿内容**；并要求草稿真的写入沙箱副本（`draft_applied`），否则"原有事实还在"只是没改过的假象 |
| M4 | 记录到的检索结果忘了回传给结果对象 | 一整轮"检索调用率 0/30"等指标全部失真 | 修回传，并加 **harness 不变量**：工具事件与落库 stub 不一致、有检索调用却零记录 → 记为该次运行的错误，不静默 |
| M5 | "无答案"用固定短语表判定 | 把「没有。…**没有命中**任何相关内容」这种**正确**回答判成失败 | 改为「否定词 + 存在性动词」的窗口规则；并新增 `--rescore`：**复用已存模型输出、只重算判定**，重算是幂等的 |
| M6 | 门槛口径与计划允许项冲突：调用率按全部历史场景算，而计划允许追加场景只走 `list_files` + `read_file` | 把"该不该检索"的行为差异误报成失败（同一配置两次运行 7/12 与 11/12） | 门槛只统计**真正依赖检索**的场景（问答 + 无答案），追加场景另报；改动记入 [rag-quality.md](../evaluations/rag-quality.md) 并作为对计划的偏离报备 |

由此形成两条硬规则，后续任何评测改动都适用：

1. **区分"模型失败"与"测量失败"**：前者记入质量结论，后者记入运行错误并修工具，两者不混。
2. **修口径不改行为**：口径修订只重算已有输出（`--rescore`），不为了数字去调产品行为；前后不一致说明落盘结论与规则已脱节。

## 2. 做法：什么方式

顺序本身是这一轮最重要的方法，缺一环都会得出错误结论：

1. **先冻结再优化**：10 篇语料字节级复制、排除项逐条记录；查询与证据用**脚本从正文推算偏移**，`quote` 必须等于切片，坏标注硬拒绝。
2. **两层评测**：检索层（真 `RetrievalService` + 每次独立 Chroma）与 Agent 层（真 `ChatAgent` + 沙箱 notes/Chroma/sqlite）。先有基线，再谈优化。
3. **一次只改一个因素**：切块五项对照（char/heading、是否带标题路径、两种长度预算）、模型三项对照，其余全部固定。
4. **先记录再判断**：所有 run 的命中内容、位置、距离、失败分类都落盘；失败必归一类（排 5 名之后 / 返回片段里没有完整证据 / 映射错误 / 无片段）。
5. **holdout 纪律**：dev 选型，holdout 只在选定后跑一次对照，且**不据其调参**；用掉之后即视为"已见数据"。
6. **门槛与代价一起报**：登记 `top_k` 实际是 3（生产口径），延迟/内存/索引耗时与体积一并给出，不把"用资源换准确率"写成无成本改进。

## 4. 不足

按影响排序，都写进 [rag-v1-report.md](../evaluations/rag-v1-report.md) §10：

1. **引用只到文件级、未到章节级**（79%）：其余引用来自 `read_file` 整篇，没有原文片段。要么接受整篇引用，要么要求引用一律来自检索片段。**待决策**。
2. **没有独立人工审查**：全部语义结论都是自动判定（含代理指标与同模型 Judge）。工程验证完成，**语义审查待确认**；自动通过不等于独立验收。
3. **笔记生成质量仍未达标**（V2.2）：l01 上加工分在 2/4 与 3/4 之间摆动（阈值 3），与 v9 相比无改善。与本次检索工作无关，但会限制"记得准"的整体目标。
4. **语料与样本都小**：10 篇、dev 24 / holdout 16。门槛附近一条查询约 4–6 个百分点，单次波动可达 1–4 条（如检索调用率 7/12 与 11/12）。
5. **单机延迟噪声大**：同一 run 不同时段 p95 从 11ms 到 235ms；跨配置比较只能用安静时段的最小值，报告已注明。
6. **Docker 未验证**：镜像里烘的模型已改为 e5-small 并加了 `HF_ENDPOINT`，但本机没有跑构建。
7. **生产索引与验收配置一度不一致**：线上曾用 bge-small-zh（dev 83.3%，低于门槛）建索引；切换与重建由用户执行，方案见报告 §6.4。
8. **任务 5（修笔记建 v2 语料）未做**：`Backtracking` 重复章节、`SQLAlchemy` 标题缺空行等真实缺陷已记录但未验证其影响。
9. **模型切换功能的可复现性**：前端按模型分 collection 是对的，但选择若只存在前端状态，离线评测需要一个等价入口（评测 CLI 已有 `--model`/`--chat-model` 可对齐）。

## 5. 未来优化（按触发条件，不预先堆组件）

| 方向 | 触发条件 | 第一步 |
|---|---|---|
| 章节级引用 | 决定要求引用一律来自检索片段 | 在提示词里限定引用来源，再跑 Agent holdout 对照 |
| rerank | 出现"候选内有证据但排名低"的失败样例 | 记录重排前候选召回与重排后命中，并把资源与延迟计入 |
| 关键词 + 向量融合 | 出现"精确词（API 名、版本号）始终漏召回" | 先只做名次融合，不同比例的原始分数不相加 |
| 返回条数 3 → 5 | 出现"第 4–5 名有答案"的失败样例 | 对比 token 成本与命中率；当前 holdout Hit@3 已 11/12，不是瓶颈 |
| BGE-M3 / 更强多语言模型 | 需要更高召回且有可接受延迟预算 | 先声明取舍（CPU 上约 25 倍算力），再固定语料对照 |
| 语料扩容到 30–50 篇 | 现有失败样例不再有代表性 | 复用 corpus v2 流程：manifest 哈希 + 逐篇审查 + 偏移重算 |
| 独立 Judge | 需要对笔记质量做正式比较 | 选与生成模型不同的 `JUDGE_MODEL`，否则只能标 `judge_independent=false` |
| 任务 5（语料 v2） | 想量化"笔记本身差"的影响 | 只改语料副本，真实 `notes/` 不动 |

## 6. 可复用的结论

1. **先有可信的测量，再谈优化**：本轮 6 个测量问题里任何一个没修，后面的选型结论都会不同（尤其 M4 会让整轮指标失真）。
2. **选型的第一判据是硬约束，不是榜单**：`max_seq_length` 覆盖不了块长度，模型一开始就是坏的——这条比"哪个模型更好"更早该问。
3. **一次只改一个因素**，并把每个因素的收益说清：本轮"章节切块"单独只提升 Hit@3，真正的大头是**把章节路径带进嵌入文本**；把两者混在一起报就会归因错误。
4. **代价要一起报**：准确率提升往往用资源换（本机 +350MB、1.6 倍延迟），声明取舍比宣称"更优"诚实。
5. **门槛冲突要修测量、记偏离，不为数字调行为**：调用率口径那次，改的是测量边界，不是让模型多调用一次检索。
6. **用掉 holdout 就是"已见"**：再按它改方案必须补新样本，否则盲测的说法不再成立。
