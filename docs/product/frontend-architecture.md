# 前端产品结构与架构决策

**状态：** 首轮已实施（2026-09-28）。五个一级页面已落地，Vue 工程与顶部导航已成为默认界面；
Records 仍只有入口与空状态，其承载的来源尚未决定。

**更新日期：** 2026-09-28。

**依据：** 用户已确认五个一级页面、Chat / Documents 的归属迁移，以及引入 Vue 框架的方向，并要求将设计与技术决策保存在 `product`。

**本文职责：** 记录前端为什么改、改成什么结构，以及准备承载哪些能力。本文不是 Agent 执行计划，执行细节与验证证据见
[2026-09-28 Vue 引入执行计划](../plans/2026-09-28-vue-frontend-initialization.md) 与
[执行记录](../plans/2026-09-28-vue-frontend-initialization-results.md)。

**当前实现：** 见 [现行前端架构](../architecture/frontend.md)。界面已是 Vue 3 SPA（`frontend/`），
由 FastAPI 托管 `web/dist` 产物，`FRONTEND_MODE=legacy` 可回退到旧模板。
本文档中「后续扩展方向」一栏仍是方向而非承诺——五个页面不等于五项能力都已交付。

## 1. 问题与目标

现有 Chat / Documents 已能承载聊天、草稿审批、笔记编辑与引用，但后续还需容纳视频记录、会议记录、来源回看和整理工作。若所有能力持续加入聊天页，功能入口和状态管理会逐渐难以理解。

本次前端演进有两个目标：

1. 建立稳定的产品导航，让助手、已保存材料、记录功能和设置各自有明确归属。
2. 引入 Vue 来组织页面、可复用组件及交互状态，为逐步接入新能力提供基础。

页面框架建设与视频/会议能力交付分别验收。拥有 Records 页面不能代表已经支持音视频采集、实时字幕或多模态笔记。

## 2. 已确认的决策

| 决策 | 内容 | 理由与影响 |
|---|---|---|
| 五个一级页面 | Home、Assistant、Library、Records、Settings | 为后续功能提供稳定归属，避免继续全部集中在聊天页 |
| Chat 归入 Assistant | 现有会话、聊天、问答与草稿交互由助手承接 | 保留已有入口能力，同时允许记录功能独立发展 |
| Documents 归入 Library | 现有笔记浏览、管理、编辑由资料库承接 | 资料库作为已保存成果的统一入口 |
| Records 承载记录功能 | 视频记录、会议记录等功能及对应记录过程归入这里 | 用户可以围绕正在记录的内容工作，具体子页面另行设计 |
| Settings 独立 | 配置能力有独立页面归属 | 设置不再只能依附聊天输入区；是否保留快捷入口另行决定 |
| 引入 Vue | 采用 Vue 组织新的前端 | 用组件和明确的状态归属承接复杂交互；不在本文件预定组件库、工程模板或具体版本 |
| 上层设计统一放 product | 本文记录结构与决策，plans 引用它分解任务 | 避免执行计划成为第二份技术设计主文档 |

这里的五个“页面”指产品一级区域，不要求五套独立应用，也不等于五个后端接口。页面路径和旧地址兼容方式属于后续详细设计。

## 3. 页面职责与功能归属

| 页面 | 主要职责 | 现有能力归属 | 后续扩展方向 |
|---|---|---|---|
| Home：首页 | 统一产品入口，帮助用户开始或继续工作 | 可连接现有助手和资料库 | 记录入口、待处理事项、最近材料；展示项目取决于真实数据支持 |
| Assistant：助手 | 自由对话、知识问答、通过对话提出整理要求 | 会话管理、SSE 回复、工具过程、引用查看、草稿编辑与审批 | 针对指定材料提问、综合已有材料、发起整理 |
| Library：资料库 | 浏览、管理、阅读和编辑已保存材料 | Documents 的笔记与目录操作、编辑预览、索引状态 | 来源追溯、多形态成果和再次加工 |
| Records：记录 | 视频、会议等记录功能入口与记录工作区 | 尚无完整的独立记录工作区 | 开始/暂停/结束记录、字幕与关键画面、重点标记、会后或观看后整理 |
| Settings：设置 | 集中管理产品配置 | 当前已有聊天模型配置、向量模型及索引管理能力可迁入 | 采集权限、整理偏好等随对应能力接入 |

各行“后续扩展方向”不是首轮全部交付承诺。当前没有真实后端支持的状态、数量、记录或任务，不得用模拟数据造成已实现的印象。

### 3.1 Records 与 Library 的边界

Records 面向记录来源及处理过程，Library 面向用户确认保存的成果。例如一次课程记录可包含字幕、PPT 画面与时间位置，之后可整理成详细笔记或重点摘要；保存后的成果进入 Library。

这一关联复用现有[业务定义](business-architecture.md)与[术语](../../CONTEXT.md)。来源、采集记录、未审批草稿不能仅因显示在页面上就自动成为正式材料。

### 3.2 Assistant 与 Records 的关系

Assistant 保留自由对话入口；Records 为具体记录功能提供工作环境。记录中补充要求、修改整理方式等对话交互可以嵌入对应工作区，具体布局及共享状态需另行设计。

本轮不决定将现有会话草稿改为独立任务草稿，也不因页面调整擅自迁移草稿存储模型。独立任务及恢复行为继续依据路线图设计与交付。

## 4. 用户场景与长期体验目标

### 指定内容生成笔记

用户指定文本或其他已支持来源并提出整理要求，系统生成草稿，用户核对和修改后保存。后续支持更多来源时，继续保留来源与整理结果的关联。

### 与用户一起观看视频

用户期望系统理解画面、PPT、图表及老师的讲解，形成高质量且可复用的笔记。目标需要保留画面与讲解的时间对应关系，支持回看依据；只有音频转写不能代表该最终目标已经交付。

获取方式允许分阶段实现。当前倾向先探索边看边记录，之后再扩展用户选择其他方式。视频来源范围、采集方式、关键帧策略和第一阶段的质量门槛尚未确定，不在本次前端文档中代选。

### 会议记录

目标包括过程中自动生成字幕或转写，结束后由用户选择整理重点、纪要或其他成果。原始记录与整理结果应当可区分，后续再次整理不应依赖重新采集。

发言人区分、音频获取、屏幕共享内容关联以及在线会议平台适配均需独立界定范围，不能因为有会议入口就宣称已支持。

## 5. 首轮前端交付范围建议

**本节状态：建议，尚未形成可直接交给 Agent 的执行规格。** 用户已确认总体页面和 Vue 方向；以下是将方向落地的候选边界，详细设计确认后再进入 plans。

1. 建立 Vue 前端基础与统一导航，形成五个一级页面的清晰入口。
2. 将现有 Chat 能力完整迁入 Assistant，将 Documents 能力迁入 Library。
3. 将现有模型及索引设置能力组织到独立 Settings 页面，保持配置和生效行为一致。
4. Home 提供可用的开始入口；近期或待处理信息仅在已有真实接口支持时展示。
5. Records 首轮可先明确功能入口与支持状态；尚未接入的记录能力清楚标为未开放，不提供无效的开始按钮或虚构进度。
6. 先定义并实现前后端接入、构建部署和兼容方案，再逐步接入新的记录功能。

本轮前端迁移不自动包含音视频采集、实时识别、独立任务服务、材料版本系统或网页抓取。这些能力按[版本路线](roadmap.md)各自交付，不能被前端计划隐式提前或省略。

## 6. 迁移必须保持的行为

迁移范围一旦确认，以下现有用户能力应作为回归检查项，以[现行前端说明](../architecture/frontend.md)和对应代码核查完整清单：

- 会话创建、列表、切换、重命名、删除与历史恢复。
- SSE 流式回复、工具过程、失败反馈和发送互斥。
- 待审草稿恢复、编辑保存、审批、拒绝以及已有的动作调整入口。
- 未保存编辑保护；切换会话时草稿与引用内容不会串到其他会话。
- 引用查看、定位及现有的笔记编辑保存路径。
- 笔记与文件夹管理、正文编辑/预览、索引状态与同步行为。
- 聊天模型配置、本地向量模型切换/修复及维护窗口中的操作限制。

AI 生成内容仍经用户审批才写入正式笔记；用户直接编辑继续走现有确定性保存路径。更换页面或框架不能削弱这两条行为边界。

新页面名不要求改后端 API 名。例如 Assistant 的页面路由与现有 `POST /chat` 可以分别演进；是否调整 API 必须有独立理由与兼容设计。

## 7. 技术取舍及待确定事项

继续在当前模板中增加功能，短期迁移成本低，但会延续页面、DOM 操作与交互状态集中维护的方式。引入 Vue 是本次已确认的方向，其代价是需要工程构建、组件拆分、部署接入和迁移回归。本文不声称 Vue 本身能解决生成质量或后端可靠性问题。

下列事项应在本文件后续修订或关联的 product 专题设计中明确，再生成 Agent 执行计划：

| 事项 | 需要作出的选择 | 影响 |
|---|---|---|
| 工程与语言 | Vue 版本、JavaScript/TypeScript、构建工具及工程目录 | 开发、构建和维护方式 |
| 页面路由 | 页面 URL、默认首页、旧地址兼容、刷新/深链接处理 | 已有使用入口与部署接入 |
| 组件与样式 | 页面布局、组件库、编辑器、响应式与交互规范 | 产品呈现与迁移成本 |
| 状态管理 | 会话、流式回复、草稿、未保存编辑、设置的状态归属 | 跨页切换与并发请求正确性 |
| 后端接入 | 开发代理、静态资源托管、SSE 连接与错误处理 | 本机运行和正式部署 |
| 首轮交付 | Home 展示范围、Records 支持状态、设置快捷入口 | 实际可用功能与验收边界 |
| 迁移节奏 | 分批接入或整体替换、过渡期入口、回退办法 | 避免中断现有功能 |

这些是明确的未决问题，不是授权执行者随意补齐的实现细节；影响产品行为或范围的选择需先在上层设计中确认。

## 8. 验收方向

首轮范围确认后，执行计划需把以下方向细化为实际检查步骤：

1. 五个一级入口职责明确，用户可以进入对应区域并理解当前支持范围。
2. 现有聊天、资料管理、草稿审批及模型设置能力在迁移后保持可用。
3. 页面切换、刷新、流式响应中断和未保存内容处理符合已确认设计，不串会话、不静默丢失编辑。
4. 配置显示与后端实际生效状态一致，维护中的操作限制明确。
5. 未实现的视频或会议能力不被展示为已实现；Records 的界面验收不替代记录能力验收。
6. 有可重复的构建/启动方式及适合关键交互的验证证据，落地后同步现行架构和操作指南。
