# 产品文档版本

当前版本线：[1.5.0 目录，修订 1.5.1 已核对确认](1.5.0/README.md)。已固定基线为 `docs-v1.5.0`；本次基线标签名为 `docs-v1.5.1`，创建结果见执行报告与 Git。文档版本不代表同名软件发布，也不改变已有代码 tag `v1.0.0`。

版本目录收纳业务、需求、功能和交付证据的当前正文；外层 `product/` 只保留索引、需求池和归档。文档版本号采用 `主版本.次版本.修订号`；同一版本线内的修订（如 `1.5.1`）继续编辑 `1.5.0/` 中受影响的文件，并在该目录的 `CHANGELOG.md` 记录已确认的变更。形成新的业务范围并确认下一条版本线时，才新建版本目录，例如 `1.6.0/`。普通草稿和进度提交不自动升级文档版本。

每次正式确认文档基线时，先核对变更及链接，再为对应的 Git 提交创建带说明的 `docs-vX.Y.Z` 标签。已发布标签不改指向；旧版本内容通过标签查看。版本号与标签的对应关系记录在版本目录的 `README.md`。后续版本如需继承既有要求，应引用上一基线及变更项，避免复制整套正文。

重要需求变更至少记录需求编号、原因、影响范围、决定、验收条件变化和对应提交；实现状态仍以实际验证证据为准。文档版本与代码发布独立编号，交付说明中再关联代码提交或发布 tag。

## 日常迭代流程

1. 新想法先写入 [需求池](../backlog.md)，说明用户场景和要解决的问题；讨论稿用普通 Git 提交保存，不自动进入已确认范围。
2. 决定纳入当前版本线时，为需求分配稳定编号，修改 [需求正文或索引](1.5.0/requirements.md)与受影响的业务规则、[功能映射](1.5.0/features.md)。已有要求的详细条款仍在 [路线图正文](1.5.0/roadmap.md)；不要在索引中复制一份。
3. 在实施前明确验收条件和排除项，并让执行计划引用需求编号。需求改变后，检查设计、计划及测试是否需要一起调整；在 [变更记录](1.5.0/CHANGELOG.md) 写明原因、决定和影响。
4. 实现后将代码提交、测试和评测报告链接回 [交付入口](1.5.0/delivery.md)，按证据更新路线图中的状态。已实现、待验收与已验收分别记录。
5. 当一组范围或要求经过核对并正式确认时，递增文档修订号（1.5.1 之后为 1.5.2），更新当前版本目录的 `README.md` 和 `CHANGELOG.md`，提交后创建对应的 `docs-v1.5.2` 标签。已有标签保持不变。

如果下一轮要建立不同的业务范围，先确认本轮目标、继承的要求和变更项，再建立新版本线目录。旧版本目录可在其 Git 标签中还原，新的目录只写必要的新增与变化，并在入口说明继承哪个基线。
