# V2.4 指定 URL 网页读取设计

**状态：** 用户已确认首版使用指定 URL、服务端直接请求和 Trafilatura 正文提取；后续允许以 API 读取器替换。产品范围以 `NoteAgent-docs/docs/02-requirements/REQ-009-可信网页来源.md` 为准。

## 用户流程

用户在当前会话给出一个或多个 URL。模型调用 `read_webpage(url)` 读取每个 URL；即使整理意图不清，也先读取，再询问用途。获取结果逐项报告成功、部分获取或失败。模型只在用户要求成文时提出 `propose_note` 草稿，笔记须经过现有审批流程。采用网页内容的成品笔记末尾列出实际使用的 URL；抓取失败后由用户粘贴内容时注明“内容由用户提供，网页未成功获取”。

首版没有主题搜索、自动找 URL、浏览器渲染或登录流程。`read_webpage` 是读取指定页面的工具；未来的 `search_web(query)` 才负责按主题发现 URL。

## 读取器接口与实现

`read_webpage(url)` 是给模型调用的稳定工具名。其内部只依赖 `WebPageReader.read(url) -> WebPageResult`；结果包含请求 URL、最终 URL、标题、正文、获取状态和简短错误。首版 `HttpTrafilaturaReader` 使用 HTTPX 发起 HTTP(S) 请求，用 Trafilatura 从 HTML 中提取正文。它限制网络耗时、响应字节和模型可接收的正文长度；截断时返回 `partial`，不能称为完整读取。用户提供多少 URL，就逐个尝试，不另设产品层面的 URL 个数上限。

网页读取器负责 URL 校验、重定向目标检查、内网地址防护、登录/人机验证迹象和提取失败分类。网页内容视为低信任数据；页面文本不能改变 Agent 的系统规则或工具权限。

后续如采用第三方提取 API，新读取器实现同一接口，在应用装配处替换；工具名、结果字段、Agent 的消息流和笔记审批契约不变。首版不加入供应商选择配置，也不接搜索或提取 API。

## Agent、上下文与保存

模型在本轮看到 URL 后主动调用 `read_webpage`。现有 `tools_node` 把包含正文的工具结果写成 `ToolMessage`，随运行状态进入 checkpoint；随后 `build_pack` 在同一回合下一次模型调用中加入完整工具消息。不另写网页本地文件、网页来源库或快照。

回合完成时，现有 `finalize_node` 清空活跃的 `runtime_messages`。历史 checkpoint 可以保留当时的完整工具结果，但后续回合的模型输入不会自动重放该正文；如果上下文没有可用正文，模型再次调用 `read_webpage`。不同会话的网页结果不复用，已审批笔记仍可跨会话检索。

系统提示要求模型对本轮用户提供的 URL 逐个调用工具，但仅靠提示不能从机制上保证全覆盖。验收必须使用实际模型检查一个和多个 URL 的调用情况；若出现漏读，本版需在发布前修正提示或增加仅针对漏读的路由兜底。

## 笔记来源与验收

网页来源仅在笔记草稿中记录实际采用的 URL，用户能在审批预览中看到最终来源栏。普通对话不强制生成草稿或来源栏。向已有笔记追加网页内容时，如果原笔记已有来源栏，需要在审批前构造并展示合并后的完整 Markdown，批准后只保留一个末尾来源栏。

验收覆盖：固定 URL 正常读取、多个 URL 部分失败、无明确整理意图、登录/人机验证、正文过长、抓取失败后用户粘贴、网页提示注入、同回合模型输入含完整工具结果、中断恢复、后续回合按需重新读取、跨会话隔离、草稿审批和来源栏合并。

## 复审后的具体约束（2026-10-11）

- URL 校验须约束实际 TCP 连接地址：每次连接及重定向均验证目标，连接到已验证的公网 IP；不继承环境代理，避免校验域名与实际代理连接脱节。HTTP 请求仍保留原域名的 Host 与 TLS 校验。
- `propose_note` 对网页相关草稿显式接收 `source_urls` 与 `user_supplied_source_urls`；未采用网页时两者为空。来源证据包括本会话当前及历史 `read_webpage` 工具步骤，删除提案无需来源参数。
- 读取失败的 URL 仅在后续用户消息表明提供了网页正文时，才能作为“内容由用户提供”的来源。已有笔记的正文若保留，原来源也保留；追加到已有来源栏时，草稿先显示完整合并结果，审批后用覆盖写入保持一个末尾来源栏。
- 自动化回归覆盖上述边界；真实模型的网页笔记成稿质量仍须单独验收，不能以 URL 工具调用覆盖率代替。
