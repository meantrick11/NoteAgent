## 5. 输入

```text
请把下面这份关于 SQLite WAL 模式的教程整理成笔记记下来，定义、操作步骤、例子和限制都不能漏，不要压成提纲。

1. WAL 是什么
SQLite 默认使用回滚日志：写事务开始时先把原始页面拷进日志文件，提交时再把改动写回主数据库文件。这种方式下读写互斥，一个写事务会挡住读。WAL 是预写式日志的简称，它换了一种做法：改动先追加到 app.db-wal 这个日志文件，主库文件保持不动，只有到检查点的时候才把这些改动合并回主库。因为读依然读主库，写只改日志，两者可以同时进行，写不再阻塞读。需要注意的是，WAL 改变的是并发行为，不是查询速度：单条查询慢仍然是索引问题，和有没有开 WAL 无关。

2. 打开 WAL 模式
打开 WAL 只要一条 PRAGMA 语句：先打开数据库，再执行 PRAGMA journal_mode=WAL; 这条设置是持久化的，它写在数据库文件头里，下次再打开仍然是 WAL，不需要每次连接都执行。查询当前模式用 PRAGMA journal_mode;，返回 wal 就说明已经生效；如果返回 delete，说明这条语句没有执行成功，或者中途被别的地方改了回去。WAL 与内存数据库不兼容：内存数据库始终是 memory 模式，因为内存库没有可以存放日志的文件，这一点在写测试时要留意，测试里的内存库不会复现 WAL 的行为。

3. 读写并发怎么变了
在回滚日志模式下，同一时刻只允许一个写事务，而且写的时候读会被挡住。WAL 模式下允许多个读事务与一个写事务同时进行：读看到的是写事务开始之前的快照，写只做追加，两边互不干扰。这带来一个直接后果：读到的数据可能比最新提交的数据旧一到两个事务。在很多缓存型读取里这可以接受，但需要读到最新值的场景要额外处理，例如写入之后立刻读回校验，就要显式开启一个写事务或者换连接再读。

4. 一个具体的例子
假设 app.db 已经开了 WAL，此时有两个连接。连接 A 执行 BEGIN IMMEDIATE; 然后 UPDATE orders SET status='paid' WHERE id=42; 但还没有提交。连接 B 在同一时刻执行 SELECT status FROM orders WHERE id=42;，它读到的仍然是旧值 pending，因为 A 的改动还留在 WAL 里没有提交。等 A 提交之后，B 新建一个事务再读，就能看到 paid。如果 A 最后回滚，WAL 里的这一页会被标记作废，B 从头到尾都只看到 pending。

5. 什么时候不要用 WAL
WAL 需要额外的 wal 与 shm 两个文件，读连接依赖共享内存，所以不适合放在不支持共享内存映射的网络文件系统上，比如某些 NFS 与 SMB 挂载，放上去之后可能出现读到旧数据甚至数据库损坏。它同样不适合同一个数据库文件被多台机器同时读写的场景。另外备份时不能只拷主库文件，要连 wal 一起拷，或者先执行 PRAGMA wal_checkpoint(TRUNCATE); 把日志合并回主库再拷，否则备份会丢掉最近的事务。

6. 检查点与日志体积
wal 文件通常不会自动无限增长：SQLite 在一千页左右会做一次自动检查点，把日志内容合并回主库。也可以用 PRAGMA wal_checkpoint(PASSIVE); 手动触发一次。需要注意，长时间打开并且一直只读的连接可能阻止检查点推进，导致 wal 持续变大，这在常驻服务里要留意，解决办法是让只读连接定期结束事务。

7. 从回滚日志迁移过来
已有数据库直接执行 PRAGMA journal_mode=WAL; 就够了，SQLite 会自己完成切换，不需要导出再导入，也不用停机。切换之后建议执行一次 PRAGMA wal_checkpoint(TRUNCATE); 让日志干净起步。如果之后想切回去，执行 PRAGMA journal_mode=DELETE; 即可，切换前会把 wal 里的内容合并回主库。

8. 常见误解
有一种误解是 WAL 能提升单条查询的速度，实际上它主要改变并发行为而不是查询本身的快慢，单条查询慢通常还是索引问题。另一种误解是 WAL 可以让多进程同时写同一个库，实际上写仍然只有一个，WAL 放开的只是读与写之间的并行；写与写之间依然会互相等待，所以高并发写入仍然要靠队列或者分库来化解。

9. 与备份工具配合
用文件拷贝的方式备份 WAL 数据库是不安全的：拷贝进行到一半时可能有检查点在写主库，拿到的会是一份不一致的快照。稳妥做法有三种：一是用 SQLite 自带的在线备份接口，它按页读取并加锁；二是先执行 PRAGMA wal_checkpoint(TRUNCATE); 把日志合并回主库再拷；三是借助文件系统快照，在快照完成的瞬间整组文件是一致的。如果确实要直接拷文件，至少要把主库、wal、shm 三个文件一起拷，并且放在同一个快照里。

10. 参数与观测
PRAGMA journal_size_limit 用来限制检查点之后 wal 文件保留的大小，避免日志文件在磁盘上长期占着空间不释放，典型设置是几十 MB。观测 WAL 状态可以读 sqlite3 里 PRAGMA wal_checkpoint; 的返回值，它依次给出日志页数、已回写的页数和是否被阻塞；被阻塞通常意味着有长事务一直没结束。

11. 和其他模式的关系
journal_mode 取值有 delete、truncate、persist、memory、wal 和 off，前面几种都属于回滚日志的变体，区别只在提交之后日志文件是删除、截断还是保留。MEMORY 模式把日志放内存，速度更快但崩溃会丢数据，只适合临时库。OFF 完全没有日志，只在可以随时重建的数据上才考虑，业务库不要用。
```
