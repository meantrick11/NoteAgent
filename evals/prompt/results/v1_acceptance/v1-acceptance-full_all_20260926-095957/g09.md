## 5. 输入

```text
请把下面这份定时任务的对比材料整理成笔记记下来，三种方案和比较维度都要有，比较结论不要少。

1. 方案一 cron
cron 是操作系统自带的定时器，用一行 crontab 就能表达按分钟、小时、天触发的任务。它的优点是零依赖、随处可见、写法简单；缺点是精度只到分钟，没有任务状态记录，失败之后不会自动重试，也没有并发控制，同一台机器上的任务互相看不见。日志默认写进系统邮件，排查问题时需要自己重定向到文件。另外 cron 的环境变量很少，脚本里依赖 PATH 的命令经常在手动执行时正常、放进 crontab 就失败。

2. 方案二 systemd timer
systemd timer 用一对单元文件描述触发时间和要执行的命令，和 service 结合使用。它比 cron 多了几样能力：支持单调时间与日历时间两种触发方式，可以表达错过触发窗口之后是否补跑，可以通过单元状态查到上次执行结果，也可以设置依赖关系和资源限制。代价是写法比 crontab 长，而且在容器里通常拿不到 systemd，这套方案只适合直接跑在宿主机上的服务。

3. 方案三 队列调度
队列调度把定时任务交给调度器和服务进程：调度器按计划把任务投递到队列，工作进程从队列里取任务执行。它的优势是任务状态、重试、并发控制和幂等都在框架内解决，多实例部署时天然只有一个实例拿到任务；缺点是引入了一套需要运维的中间件，部署和排查都更重，任务量和复杂度不大的时候属于过度设计。

4. 比较维度
从五个维度比较：依赖与部署成本，cron 最低，队列调度最高；触发精度，cron 到分钟，systemd timer 可以到秒，队列调度取决于调度器精度；失败重试，只有队列调度内置；观测能力，systemd timer 有单元状态，队列调度有任务记录，cron 几乎没有；多实例去重，队列调度有，另外两种都需要自己实现，例如加文件锁或者用数据库抢占。

5. 选择建议
单机上的简单清理和报表，用 cron 就够了；如果机器用 systemd 管理，并且需要看执行结果或者需要错过补跑，换成 systemd timer；任务需要重试、需要观测、或者将来要跑在多台机器上，直接上队列调度，不要用 cron 加锁去拼，那只是在重新发明调度器。

6. 迁移时要注意
从 cron 迁到 systemd timer 时，原来的环境变量要显式写进单元文件，不要指望 shell 配置文件被读取。迁到队列调度时，任务本身要改成幂等的，因为重试机制会把失败的任务再投一次，不幂等的任务在重试之后会产生重复的副作用。

7. 观测与告警
定时任务最容易出现的问题不是没跑，而是跑了没人知道结果。cron 需要自己把输出重定向到文件，再额外加一段检查；systemd timer 可以用 systemctl list-timers 看下次触发时间和上次触发时间；队列调度天然带任务记录，失败任务会进入重试队列，需要配一个失败率的告警。三种方案都建议加一条心跳：即使任务本身不做事，也要让外部监控知道调度器还活着。

8. 时间与时区
cron 按机器本地时区解释时间表达式，容器里通常是 UTC，这一点在跨时区部署时经常造成任务提前或推迟几个小时；systemd timer 可以用 UTC 或本地时区，写法上要显式声明；队列调度器通常按调度器自身的时区执行，任务参数里最好带上业务时区。夏令时切换当天，按小时触发的任务可能出现重复或跳过，按天触发的任务建议避开切换时刻。

9. 幂等与补偿
无论用哪种方案，任务本身都应该写成可重复执行的：被重试、被手工补跑、或者因为时钟回拨被执行两次，都不应该产生重复数据。做不到幂等的任务，要在任务内部记录执行批次，并在开始时先检查本批次是否已经完成，这就是补偿逻辑，它比事后清洗数据便宜得多。

10. 失败之后的处理方式
cron 失败之后没有内置的重试，要靠任务自己在脚本里重试，或者在下一轮触发时顺便补齐；systemd timer 可以通过单元的 Restart 和 OnFailure 做有限的重试与告警；队列调度把失败任务放回队列并按退避策略重投，还能配置最大重试次数和死信队列。选择方案时要先想清楚失败是常态还是异常，常态化的失败要交给调度器管。

11. 任务之间的依赖
如果任务 B 要在任务 A 成功之后才能跑，cron 里仅能把两个表达式的时间错开，靠猜 A 大概要跑多久，这种做法在 A 变慢时会静默失效；systemd timer 可以用 After 和 Requires 表达依赖；队列调度可以用任务编排或者在前一个任务的成功回调里投递下一个任务，依赖表达得最清楚，但要防止形成环。

12. 长任务的取舍
超过触发间隔的长任务会让 cron 出现重叠执行，需要自己在脚本里加锁；systemd timer 同样不会因为上一次没结束就跳过下一次，锁还是要在脚本里加；队列调度本身有并发度设置，可以把同一类任务的并发限制为一，天然避免了重叠。重叠执行带来的往往是重复写入，所以这一条要和幂等一起考虑。

13. 成本与复杂度
三种方案的成本差距主要在运维上：cron 几乎零成本，systemd timer 复用已有的服务管理能力，队列调度意味着多一套中间件、多一份监控和多一类故障。选型时先问自己失败会不会有人发现，如果不会，那么多花的复杂度是买观测能力，通常是值得的。
```
