## 5. 输入

```text
请把下面这篇关于幂等性的技术文章整理成笔记记下来，概念之间的关系和适用边界都要保留，不要加材料里没有的结论。

1. 幂等的定义
幂等指同一个操作执行一次和执行多次，对系统状态产生的结果相同。注意这里说的是最终状态相同，不是执行过程相同：一个接口第一次调用创建订单，第二次调用返回同一个订单，这仍然是幂等的。反过来，只要重复执行会多产生一条订单，无论实现多优雅，它都不幂等。

2. 幂等与重试的关系
重试是分布式系统里绕不开的：调用方超时之后无法判断请求是否已经被处理，只好重发。如果被调方不幂等，重试就会产生重复数据。所以幂等是重试的前提条件，没有幂等，超时重试这个动作本身就是危险的。反过来说，一个幂等的写接口可以让调用方放心地重试，而不需要引入复杂的分布式事务。

3. 幂等键
实现幂等最常用的方式是幂等键：调用方为每一次业务意图生成一个唯一键，随请求一起发送；服务端在第一次处理时把这个键和处理结果一起记录下来，之后遇到同样的键就直接返回上次的结果，不再重复执行。键的选择决定了幂等的粒度：用订单号做键，同一个订单不会被重复创建；用请求 ID 做键，则每次新的业务意图都需要新的请求 ID，同一个请求 ID 重发才会被识别为重复。

4. 状态记录的位置
幂等键的存储位置会直接影响可靠性。放在进程内存里最简单，但进程重启就丢失，只适合开发环境。放在关系库里通常就够用：键上加唯一索引，插入冲突就意味着重复请求，处理逻辑可以放进同一个事务里。放在独立的缓存里速度更快，但要考虑缓存的过期策略和持久化，一旦键过期，重复请求就可能被当成新请求处理，所以缓存的过期时间要明显长于调用方的重试窗口。

5. 适用边界
幂等主要解决重复提交与超时重试带来的副作用，它不解决并发写覆盖，也不保证顺序。有状态迁移的操作要额外小心：只允许从待支付迁到已支付，而不允许反向，这类约束要靠状态机本身表达，单靠幂等键覆盖不到。另外，如果操作本身包含不可逆的外部副作用，比如已经发出的短信，幂等只在接口层面保证不重复调用，已经发生的外部行为无法撤销，这类接口要尽量把副作用后置到确认成功之后。

6. 常见误区
把幂等理解成接口可以随便调用是一种误解，它保证的是结果一致，不是没有成本：每一次重复请求仍然会走到服务端，仍然消耗资源。另一种误解是把幂等键当成请求去重，实际上键的语义由业务定义，同一个键对应同一个业务意图，如果调用方把不同的意图用同一个键发送，第二次就会被错误地当成重复请求而被忽略。

7. 幂等与并发控制
幂等和乐观锁常被放在一起讨论，但解决的是两件事：幂等解决重复请求，乐观锁解决并发覆盖。两个请求同时修改同一条记录，都读到旧值再写回，后写的会覆盖先写的，这种情况需要版本号或者条件更新来拦住，幂等键帮不上忙。实际系统里两者通常同时使用：幂等键挡住重发，版本号挡住并发覆盖。

8. 落地时的检查清单
落地一个幂等接口时逐项确认：幂等键从哪来、由谁生成；键的存储放在哪里、过期时间是否长于客户端重试窗口；处理结果是否和键在同一个事务里落库，避免出现键写进去了但业务数据没写；重复请求返回的是原结果还是成功提示。这几项里最容易出错的是第三项，键与业务数据分属两个存储时，两者之间的一致性要靠补偿或者最终一致来处理。

9. 与业务去重的关系
业务去重限制的是结果本身，比如同一个用户同一天只允许领一次优惠券；幂等限制的是同一次意图被重复提交。前者是业务规则，即使调用方换了新的请求 ID 也不允许；后者是传输层的保障，只认同一个键。把两者混为一谈会导致规则漏掉，领券这种场景需要的是业务去重，而不是靠幂等键挡住重复提交。

10. 为什么超时不能等同于失败
调用方超时只说明它在规定时间内没等到响应，不说明服务端没有处理。网络在响应回来的路上断掉、服务端处理完但写响应时超时，这两种情况都会让调用方看到超时，而服务端其实已经成功。这正是重试会产生重复数据的根本原因，也是要先做幂等再做重试的原因。

11. 幂等键的生成方式
幂等键可以由调用方生成，也可以由服务端根据业务字段拼出来。由调用方生成更灵活，但要求调用方在重试时复用同一个键，而不是每次重试都换新的；由服务端拼键则免去了这个约定，但需要保证业务字段能唯一标识一次意图，字段选得不好会把两次不同的操作误判为同一件事。

12. 失败之后的状态
幂等键记录的不只是成功结果，还要记录失败。如果第一次处理失败并且没有记录，重试会重新执行一遍，这时如果失败发生在副作用已经产生之后，副作用就会重复。因此键表里通常带一个状态字段，区分处理中、成功和失败，重试遇到处理中的记录可以选择等待或者直接返回进行中。

13. 与事务的关系
幂等键的写入和业务数据的写入要放在同一个事务里，两者一起成功或者一起失败。如果分属两个存储，就需要用补偿或最终一致来处理中间状态，工程复杂度会明显上升，所以能用同一个数据库解决时就不要拆开。
```
