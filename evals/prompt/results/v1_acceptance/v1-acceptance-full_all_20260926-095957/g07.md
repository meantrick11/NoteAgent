## 5. 输入

```text
请把下面这份内部 API 服务的部署手册整理成笔记记下来，前提条件、安装、执行、检查、恢复都要写清楚，恢复条件不能省略。

1. 前提条件
目标机器需要是 64 位 Linux，systemd 版本不低于 240，机器上已经存在一个专用的运行账号 api-run，并且该账号对 /srv/api 目录有读写权限。部署前需要确认机器能访问内部制品库，否则安装包无法拉取；如果机器在隔离网络里，提前把安装包放到跳板机上再分发过去。还要确认机器时间同步正常，否则健康检查里的时间戳校验会失败，看起来像是服务没起来。

2. 安装
先把制品库里的 api-server-1.4.2.tar.gz 下载到 /tmp，用 sha256sum 对照发布单里的校验值，校验一致再解包到 /srv/api/releases/1.4.2。解包之后把 /srv/api/current 这个软链接指向新版本目录，而不是直接覆盖旧目录，这样出问题时可以快速切回。目录属主改成 api-run，权限保持 750，不要把配置目录开放给其他账号。

3. 执行
服务由 systemd 托管，单元文件放在 /etc/systemd/system/api.service，里面指定 User=api-run、ExecStart=/srv/api/current/bin/api-server --config /etc/api/config.yaml。改完单元文件执行 systemctl daemon-reload，然后 systemctl start api 启动，systemctl enable api 设置开机自启。启动顺序上先起配置里依赖的缓存与数据库连接，再起 api 本身，否则启动阶段就会因为连不上依赖而重启。

4. 检查
启动之后先看 systemctl status api 是否处于 active (running)，再看 journalctl -u api -n 100 有没有异常栈。随后请求健康检查接口 http://127.0.0.1:8080/healthz，返回 200 且带 version 字段说明进程正常。最后从另一台机器请求一次真实业务接口，确认网络和鉴权都没问题，本地通不代表外部通。

5. 恢复
如果新版本启动失败，把 /srv/api/current 软链接切回上一个版本目录，执行 systemctl restart api，再按第 4 节重新检查。恢复的适用条件是配置文件格式没有变化：如果这次发布同时改了配置结构，回退需要连配置一起还原，否则旧版本会因为读不懂新配置而再次失败。数据层面的变更不在软链接回退范围内，需要单独评估，尤其是这次发布如果引入了新的表结构，回退代码之后旧代码可能读不了新数据。

6. 日志与留存
服务日志统一由 journald 收集，默认保留在 /var/log/journal 下，按机器配置轮转。应用自身写出的业务日志落在 /srv/api/shared/logs 下，按天切分，保留 14 天。排查问题时优先看应用日志，systemd 的 journal 主要用来看进程是否被拉起、是否被 OOM 杀掉。

7. 常见故障
启动即退出通常是配置路径写错或者依赖服务没起来，journal 里会有一条明确的报错。进程在但接口 502，一般是端口被别的进程占用，用 ss -lntp 确认监听端口。运行一段时间后自动重启，先去 dmesg 看有没有 OOM 记录，再回头调内存限制。

8. 回退演练
每次发布前在预发布环境演练一次回退：把 current 软链接切到上一个版本，重启，跑一遍健康检查，再切回来。演练的目的是确认上一个版本目录还在、配置兼容、依赖版本没有一起消失。只做一次演练可能不够，跨版本升级比如从 1.2 直接到 1.4 时，要确认回退目标是紧邻的上一个版本，跨越多个版本的软链接回退通常不成立。

9. 配置与密钥
配置放在 /etc/api/config.yaml，权限 640，属主是 root、属组是 api-run，这样服务能读、运行账号本身不能改。密钥不要写进配置文件，而是通过 systemd 的 EnvironmentFile 从 /etc/api/secrets.env 注入，这个文件权限 600 且不进版本库。改完密钥之后要 systemctl restart api，因为配置只在进程启动时读取一次。

10. 版本与产物对应关系
发布单上写清楚版本号、制品校验值、配置变更项和数据库变更项，四者齐全才能开始部署。如果这次没有数据库变更，也要在发布单上写一句没有，而不是留空，因为留空和遗漏在事后无法区分。

11. 多实例与负载均衡
这套部署方式假设同一台机器上只跑一个 api 实例，多个实例要分布在多台机器上，由前面的负载均衡统一分发请求。不要在同一台机器上用不同端口起两个实例再挂到同一个负载均衡后面，因为本地端口争用和日志混淆会让排查变得困难。多实例部署时，每个实例的配置只差实例编号和日志路径，其余部分保持一致，避免出现只有某一台出现问题的隐性差异。

12. 数据库连接配置
连接串从 secrets.env 注入，配置文件里只写连接池参数。连接池大小按实例数乘以单实例最大连接数估算，总和要留出余量给运维工具，否则一次全量并发会把数据库连接打满。如果部署了多个实例，每个实例的池上限要按实例数下调，而不是照抄单实例的数字。

13. 发布记录
每次部署在发布单上记下时间、执行人、版本号、回退版本和观测结论。这些记录看起来繁琐，但当下一次出现只有某个版本才有的问题时，它是唯一能把现象和变更对上号的依据。
```
